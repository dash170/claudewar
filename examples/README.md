# examples

A finished project the machine would hand to a builder. Read it instead of the 300-line README if you want to know what this repo actually produces.

## `subtitle-converter/`

A dependency-free CLI that converts subtitle files between SRT and WebVTT. Small enough to read in ten minutes, real enough that the grounding signal is a real test suite and not a placeholder.

### Run it — about 60 seconds

```bash
cd examples/subtitle-converter
bash init.sh              # or: pwsh init.ps1
```

You should see:

```
[init] node v20.x.x
[init] no dependencies to install
21/21 passed, 0 failed
[verify] green=true  21/21 passed, 0 failed
```

`verify.sh` just wrote `RESULTS.json`. That file is the **evidence artifact** the ship gate names — regenerated by the run, never written by hand. That distinction is the whole idea: a claim you can regenerate is evidence, a claim you type is a claim.

Then use the thing:

```bash
node src/cli.js fixtures/sample.srt --to vtt
node src/cli.js fixtures/sample.vtt --to srt -o out.srt
```

```bash
node tests/eval_prompt.js examples/subtitle-converter --gate 85
```

```
100/100  subtitle-converter     ✓ all checks
```

Now score the empty template for contrast:

```bash
node tests/eval_prompt.js projects/_TEMPLATE
```

It scores **64**. That gap is the only honest demonstration that the scorer measures something: an unfilled skeleton has to fail, or the number means nothing.

| File | Why it is worth your time |

| `PLAN.md` | Four phases, each with its own EARS acceptance clause and the evidence that closes it. Note the **Not in scope** section: a decision, so it cannot decay into an omission. |

### Two things this example is honest about

**The study step was thin.** Both formats are published specifications, so the deep study collapsed into reading them. No market research, no reference hunt. That is recorded in the STATUS self-audit rather than dressed up, because a repo that demands real artifacts cannot fake one in its own showcase.

**The reference fixtures were generated, then hand-checked.** `fixtures/*.expected` came out of the implementation, which would make the byte-comparison tests circular — so both files were read against the format specs by hand before being trusted, and that check is recorded in the coverage ledger. A generated expectation nobody read tests nothing.

### Now make the machine do something

The interesting move is not reading a finished project. Open a fresh Claude Code **inside `examples/subtitle-converter/`** and say:

> read `PROJECT_OPERATING_PROMPT.md` and go

It will load the project `CLAUDE.md`, the three subagents, and the rails, then look for the next unchecked `PLAN.md` item. There is none — the ladder is complete. So give it one from the backlog:

> add `--shift <ms>` for re-syncing a track that drifts. Write its EARS acceptance clause in PLAN.md first.

Watch what it does before it writes code: an acceptance clause, then a failing assertion, then the implementation, then `verify.sh`. That order is the product.
